# Доска задач: PM, разработчик, QA

Три роли работают над одним репозиторием и общаются только через файлы в этом каталоге.

| Роль | Кто | Где работает | Что делает |
|---|---|---|---|
| **PM** | Codex | главный чекаут | пишет ТЗ, запускает сессии, читает отчёты, принимает работу |
| **Разработчик** | Claude, команда `/tz` | свой worktree, ветка `task/<ID>` | реализует ТЗ, пишет dev-отчёт |
| **QA** | Claude, команда `/qa` | свой worktree, detached на ветке разработчика | проверяет, ничего не чинит, пишет QA-отчёт |

## Цикл

```
todo → in-dev → ready-for-qa → qa-passed | qa-failed → rework → … → accepted
```

1. PM создаёт `pm/tasks/T-0NN-имя.md` по шаблону `pm/tasks/_TEMPLATE.md`,
   добавляет строку в `pm/board.md`, коммитит в `main`.
2. `node tools/pm-run.mjs dev T-0NN` → ветка, worktree, сессия разработчика.
3. `node tools/pm-run.mjs qa T-0NN` → сессия QA на коммите разработчика.
4. PM читает отчёты и пишет `pm/reports/T-0NN.verdict-rN.md`:
   - на доработку — `node tools/pm-run.mjs rework T-0NN --note "…"`
   - на ретест — `node tools/pm-run.mjs retest T-0NN`
5. `node tools/pm-run.mjs accept T-0NN` → merge `--no-ff` в `main`, снос worktree.

`node tools/pm-run.mjs status` — сводка по доске.

## Файлы

| Путь | Кто пишет |
|---|---|
| `pm/board.md` | PM и лаунчер |
| `pm/tasks/T-0NN-*.md` | только PM |
| `pm/reports/T-0NN.dev-rN.md` | разработчик |
| `pm/reports/T-0NN.qa-rN.md` | QA |
| `pm/reports/T-0NN.verdict-rN.md` | PM |
| `pm/state/T-0NN.json` | лаунчер (id сессий, раунд, ветка) |

## Одна доска на всех

Доска физически одна и лежит в главном чекауте:
`/Users/andreyryazanov/Desktop/apps/language_quest/pm/`.

Сессии разработчика и QA идут в отдельных worktree, но читают и пишут отчёты
**по абсолютному пути в главный чекаут** — его лаунчер кладёт в переменную окружения
`PM_ROOT`. Если бы они писали в свою копию `pm/`, отчёты осели бы в ветке
и PM не увидел бы их до merge.

Git-команды в главном чекауте выполняет только лаунчер. Сессии туда лишь пишут файлы.

## Модели

Разработчик по умолчанию идёт на Sonnet, QA — на Opus. ТЗ задаёт испанские реплики
и содержимое карточек дословно, поэтому разработчик реализует спецификацию. У QA
спецификации на то, *как* искать дефект, нет: он должен не поставить PASS там, где
«вроде работает», а ложный PASS уходит в `accept` и обесценивает конвейер.

Запускай разработчика с `--model opus`, если ТЗ оставило испанский на его усмотрение:
придумать реплику-ловушку — не реализация.

Усилие рассуждения (`CLAUDE_CODE_EFFORT_LEVEL`) разведено по той же логике:
разработчик — `medium`, QA — `max`. На доработке разработчик поднимается до `high`:
раз первый раунд что-то упустил, дефект по определению не лежал на поверхности.
Переопределяется флагом `--effort low|medium|high|max`.

## Чего этот конвейер не закрывает

- **Визуальную проверку.** Сессии headless, браузера у них нет. Всё, что надо увидеть
  глазами, QA выносит в секцию «Требует ручной проверки», и задача не принимается,
  пока эта секция не закрыта человеком.
- **Естественность испанского.** Скрипты ловят орфографию и интенты, но не то,
  как реплика звучит. Это читает PM.
